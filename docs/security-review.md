## Checklist

| Area | Result | Evidence |
|---|---|---|
| **Authorization** | OK | Fallback policy requires an authenticated user (`ApiServiceCollectionExtensions.AddApi`). `AnonymousActions_AreOnlyCsrfRegisterLoginMe` fails if any other action becomes anonymous. `/api/auth/me` is anonymous since stage 12 so a logged-out page load is not a console error: it returns 204 without a session (`Me_WithoutSession_Returns204NotRedirect`) and only ever the signed-in user's own data, from the cookie (`Me_AfterLogin_ReturnsUser`, `Me_UserGone_Returns401`). `Endpoints_WithoutSession_Return401`; unknown `/api/*` → 401/404, never `index.html` (`UnknownApiPath_WithoutSession_Returns401`, `UnknownApiPath_WithSession_Returns404NotHtml`). |
| **Data isolation** | OK | Teacher id only from the `NameIdentifier` claim (`ClaimsCurrentTeacher`); no Application request record has a teacher id (checked by grep). `TeacherB_GetsNotFoundOnEveryOperationOnTeacherAsStudent`, `TeacherB_GetsNotFoundOnEveryOperationOnTeacherAsPlan`, `Create_OtherTeachersStudent_Returns400SameAsMissing`, `List_FilterByOtherTeachersStudent_ReturnsEmpty`. |
| **Session cookie** | OK | `HttpOnly`, `Secure` (always), `SameSite=Strict`, 8 h sliding (`AddCookieAuthentication`); `Login_Valid_SetsHttpOnlySecureStrictCookie`; 401 instead of redirect (`Me_WithoutSession_Returns204NotRedirect`, `Endpoints_WithoutSession_Return401`); logout ends the session (`Me_AfterLogout_Returns204`). Keys persisted so sessions survive a restart (`Session_WithKeysPath_IsAcceptedAfterRestart`). |
| **CSRF** | OK | `AntiforgeryValidationFilter` on every unsafe method, `login` and `register` included: `Register_WithoutXsrfToken_IsRejected`, `TokenFromBeforeLogin_IsRejectedAfterLoginWithXsrfType`; the frontend refreshes the token around login/logout and retries once on a stale token (`xsrf-retry-interceptor.spec.ts`, `auth-store.spec.ts`). |
| **Passwords** | OK | Only the hash is stored (`StoredUser_HasHashNotPassword`, `Create_StoresHashNotPassword`); never returned (`UserResponse` has id, name, email) or logged (`FullFlow_LogsContainNoPasswordHashCookieTokenOrConnectionString`); length 8–128 (`Register_PasswordOf7Chars_ReturnsPasswordErrorAndCreatesNothing`, `Register_PasswordOf129Chars_ReturnsMaxLengthError`); same message for unknown email, wrong password and locked account, and an unknown email still verifies a fixed dummy hash for similar timing (`IdentityUserAccounts`, `CheckPassword_UnknownEmail_ReturnsInvalidCredentials`, `Login_LockedOut_ReturnsSameErrorAsWrongPassword`). |
| **Brute force** | OK + accepted risk | Rate limiter on `login` and `register` → 429 (`Login_FourthAttemptInWindow_Returns429`); 5 failures lock the account for 15 minutes (`Login_FiveWrongThenRight_Returns401`, `CheckPassword_FiveWrongThenRight_ReturnsLockedOut`). **Accepted:** anyone who knows an email can lock that account for 15 minutes; limited by the rate limiter. The limiter is per client IP and per app instance. |
| **Input** | **Fixed** + OK | **Fixed:** request body limited to 1 MiB → 413 ProblemDetails (`PostStudent_BodyOver1MiB_Returns413WithoutSavingAnything`; Kestrel `MaxRequestBodySize` at the same value stops chunked bodies); the longest valid lesson plan still saves (`PostLessonPlan_WithLongestValidFields_Returns201`). OK: length limits and enum checks in Domain/Application tests; numeric enums rejected (`Create_IntegerEnglishLevel_Returns400AndStoresNothing`, `ChangeStatus_IntegerStatusInBody_Returns400`, `List_NumericUndefinedStatusInQuery_Returns400`); malformed JSON → 400 without internal details (`Create_MalformedJson_Returns400ProblemWithoutStackTrace`). |
| **Errors and logs** | **Fixed** + OK | **Fixed:** EF Core logged every SQL command at Information; now Warning (`EfCommands_NotLoggedAtInformation`). OK: no password, hash, auth cookie, XSRF token or database password in any log over a full flow (`FullFlow_LogsContainNoPasswordHashCookieTokenOrConnectionString`, passed on its first run); an unhandled exception outside Development returns a 500 ProblemDetails without message or stack trace (`UnhandledException_OutsideDevelopment_Returns500WithoutDetails`). |
| **Database** | OK + accepted risk | Only EF Core LINQ, no raw SQL (grep: no `FromSql`/`ExecuteSql`); search escapes `%`, `_`, `[` (`ListByTeacher_SearchWithWildcards_MatchesLiterally`, `Contains_EscapesWildcards`). Connection string from user secrets or environment; `.env` git-ignored, `.env.example` placeholders only; SQL Server published on `127.0.0.1` only (`docker-compose.yml`). **Accepted:** the demo connects as `sa` (local demo only). |
| **Transport and headers** | **Fixed** + accepted risk | **Fixed:** every response now has `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a Content-Security-Policy (`script-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, …) — `AnonymousResponse_HasSecurityHeaders`, `ProblemDetailsResponse_HasSecurityHeaders`. To allow `script-src 'self'`, the theme script moved from `index.html` to `theme-init.js` and the production build no longer inlines critical CSS (that step injects an inline script, which the CSP would block and leave the app unstyled). `style-src` keeps `'unsafe-inline'` because Angular and Material inject component styles. No CORS policy (same origin). The `app` container runs as a non-root user (`Dockerfile`). **Accepted:** the Docker demo is plain HTTP on `localhost` (Chrome, Edge and Firefox accept the `Secure` cookie there; Safari does not); a real deployment puts TLS in front. |
| **Frontend** | OK | No `innerHTML` or `bypassSecurityTrust*` (grep); `localStorage` holds only the theme choice, no credentials (`theme.ts`, `theme-init.js`); `returnUrl` accepted only as an app path (`safe-return-url.spec.ts`: `//evil.example`, `https://evil.example`, `javascript:…`, `null`, `undefined` → `/lesson-plans`); session loss reloads the page so no previous teacher's data stays in memory (`unauthorized-interceptor.spec.ts`). |
| **Secrets and demo data** | OK + accepted risk | No secrets in the repository or the image (`.dockerignore` excludes `.env`; the password reaches the container only as an environment variable at run time). Seed only when `Seed:DemoData` is `true` (off in `appsettings.json`; on in Development and the Docker demo) and only on a database with no users (`Seed_SecondRun_ReturnsFalseAndAddsNothing`, `Seed_DatabaseWithAnyUser_AddsNothing`). Demo passwords appear only in the README and the seed. **Accepted:** data protection keys are stored unencrypted in the `dp-keys` volume (no key vault or certificate in a local demo; the host logs "No XML encryptor configured"). |
| **Dependencies** | OK | 2026-11-11, approved by the human: `dotnet list package --vulnerable --include-transitive` → no vulnerable packages in any of the 10 projects; `npm audit --omit=dev` → 0; `npm audit` → 0. |

## Accepted risks

| Risk | Why accepted | Mitigation in a real deployment |
|---|---|---|
| Demo over plain HTTP on `localhost` | Local demo; browsers treat `localhost` as secure for cookies (except Safari) | TLS in front of the app |
| App connects to SQL Server as `sa` | One-command local demo; migrations need DDL rights | A dedicated login with only the rights migrations and the app need |
| Data protection keys unencrypted in the volume | No secret store in a local demo | Protect keys with a certificate or a key vault |
| Account lockout by a third party | Lockout protects against password guessing; the rate limiter limits abuse | CAPTCHA or progressive delays instead of a hard lockout |
| Last write wins on concurrent edits | One teacher edits their own records | Concurrency token (row version) on updates |
| Rate limit per client IP and per instance | Single instance demo | Distributed limiter keyed by account and IP |
