# Security review

Stage 13 review of the finished app (backend, frontend, Docker demo) against the checklist in [plan.md §7](plan.md#security-review-stage-13), done on 2026-11-11 by reading the code, running the tests, and checking the Docker demo with real requests. An independent second reader reviewed the whole app and this document; its corrections are included. Plan: [plans/2026-11-11-6-security-review.md](plans/2026-11-11-6-security-review.md).

Each row is **OK** (the test or file that proves it), **Fixed** (regression test written first, then the fix), or **Accepted risk** (why; also in the README "Known limitations"). Test names are in `tests/` (backend) and `frontend/src` (Angular).

| Result | Items |

| Vulnerable packages | None (`dotnet list package --vulnerable --include-transitive`, `npm audit`) |

## Checklist

| Area | Result | Evidence |
|---|---|---|
| **Authorization** | OK | Fallback policy requires an authenticated user (`ApiServiceCollectionExtensions.AddApi`). `AnonymousActions_AreOnlyCsrfRegisterLoginMe` fails if any other action becomes anonymous. `/api/auth/me` is anonymous since stage 12 so a logged-out page load is not a console error: it returns 204 without a session (`Me_WithoutSession_Returns204NotRedirect`) and only ever the signed-in user's own data, from the cookie (`Me_AfterLogin_ReturnsUser`, `Me_UserGone_Returns401`). `Endpoints_WithoutSession_Return401`; unknown `/api/*` → 401/404, never `index.html` (`UnknownApiPath_WithoutSession_Returns401`, `UnknownApiPath_WithSession_Returns404NotHtml`). |
| **Data isolation** | OK | Teacher id only from the `NameIdentifier` claim (`ClaimsCurrentTeacher`); no Application request record has a teacher id, id or status (checked by grep), so nothing can be mass-assigned. `TeacherB_GetsNotFoundOnEveryOperationOnTeacherAsStudent`, `TeacherB_GetsNotFoundOnEveryOperationOnTeacherAsPlan`, `Create_OtherTeachersStudent_Returns400SameAsMissing` (HTTP), `Update_MoveToForeignStudent_ReturnsStudentNotFound` (Application level only; no HTTP test for update with a foreign student), `List_FilterByOtherTeachersStudent_ReturnsEmpty`. |
| **Session cookie** | OK + accepted risk | `HttpOnly`, `Secure` (always), `SameSite=Strict`, 8 h sliding (`AddCookieAuthentication`); `Login_Valid_SetsHttpOnlySecureStrictCookie`; 401 instead of redirect (`Endpoints_WithoutSession_Return401`); logout removes the cookie from the browser (`Me_AfterLogout_Returns204`). Keys persisted so sessions survive a restart (`Session_WithKeysPath_IsAcceptedAfterRestart`). **Accepted:** logout does not revoke the session on the server; a cookie copied before logout stays valid until it expires (up to 8 h). HttpOnly and `SameSite=Strict` make copying it unlikely. |
| **CSRF** | OK | `AntiforgeryValidationFilter` on every unsafe method, `login` and `register` included: `Register_WithoutXsrfToken_IsRejected`, `TokenFromBeforeLogin_IsRejectedAfterLoginWithXsrfType`; the frontend refreshes the token around login/logout and retries once on a stale token (`xsrf-retry-interceptor.spec.ts`, `auth-store.spec.ts`). The `XSRF-TOKEN` cookie is readable by JavaScript by design (double-submit pattern). |
| **Passwords** | OK + accepted risk | Only the hash is stored (`StoredUser_HasHashNotPassword`, `Create_StoresHashNotPassword`); never returned (`UserResponse` has id, name, email) or logged (`FullFlow_LogsContainNoPasswordHashCookieTokenOrConnectionString`); length 8–128 (`Register_PasswordOf7Chars_ReturnsPasswordErrorAndCreatesNothing`, `Register_PasswordOf129Chars_ReturnsMaxLengthError`); login gives the same message for unknown email, wrong password and locked account (`CheckPassword_UnknownEmail_ReturnsInvalidCredentials`, `Login_LockedOut_ReturnsSameErrorAsWrongPassword`), and an unknown email still verifies a fixed dummy hash so the expensive hashing work is the same; a known email also records the failure in the database, a difference of a few milliseconds. **Accepted:** register answers 409 "An account with this email already exists", so anyone can learn whether an email has an account (plan.md §5 asks for that 409). A real deployment would answer the same way for both cases and confirm by email. |
| **Brute force** | OK + accepted risk | The `auth` rate limiter (10 requests per minute per client IP) is on `login` and `register`; the 429 is tested for login (`Login_FourthAttemptInWindow_Returns429`), register uses the same policy attribute without a test of its own. 5 failures lock the account for 15 minutes (`Login_FiveWrongThenRight_Returns401`, `CheckPassword_FiveWrongThenRight_ReturnsLockedOut`). The limiter keys on the connection's IP; no forwarded-headers middleware is enabled, so `X-Forwarded-For` cannot change it. **Accepted:** anyone who knows an email can lock that account for 15 minutes; the limiter is per IP and per app instance. |
| **Input** | **Fixed** + OK | **Fixed:** request body limited to 1 MiB → 413 ProblemDetails. A body with `Content-Length` over the limit is refused before it is read (`PostStudent_BodyOver1MiB_Returns413WithoutSavingAnything`); a chunked body is stopped by Kestrel's `MaxRequestBodySize` while reading, which used to surface as a 500 and an error log — now a 413 and no error log (`BodyTooLargeWhileReading_Returns413NotAServerError`; checked on the Docker demo with a 1.2 MB chunked body). The longest valid lesson plan still saves (`PostLessonPlan_WithLongestValidFields_Returns201`). OK: length limits and enum checks in Domain/Application tests; numeric enums rejected (`Create_IntegerEnglishLevel_Returns400AndStoresNothing`, `ChangeStatus_IntegerStatusInBody_Returns400`, `List_NumericUndefinedStatusInQuery_Returns400`); malformed JSON → 400 without internal details (`Create_MalformedJson_Returns400ProblemWithoutStackTrace`). `lessonDate` binds to `DateOnly`, so a malformed date is a 400 from model binding; there is no dedicated test for it. |
| **Errors and logs** | **Fixed** + OK | **Fixed:** EF Core logged every SQL command at Information; now Warning (`EfCommands_NotLoggedAtInformation`). OK: no password, hash, auth cookie, XSRF token or database password in any log over a full flow, with Information logs captured so the check is not empty (`FullFlow_LogsContainNoPasswordHashCookieTokenOrConnectionString`, passed on its first run); an unhandled exception outside Development returns a 500 ProblemDetails without message or stack trace (`UnhandledException_OutsideDevelopment_Returns500WithoutDetails`); the JSON console logger escapes newlines, so request values cannot forge log lines. |
| **Database** | OK + accepted risk | Only EF Core LINQ, no raw SQL (grep: no `FromSql`/`ExecuteSql`); search escapes `%`, `_`, `[` (`ListByTeacher_SearchWithWildcards_MatchesLiterally`, `Contains_EscapesWildcards`). Connection string from user secrets or environment; `.env` git-ignored, `.env.example` placeholders only; no secrets in the git history. SQL Server published on `127.0.0.1` only (`docker-compose.yml`). **Accepted:** the demo connects as `sa` (local demo only). |
| **Transport and headers** | **Fixed** + accepted risk | **Fixed:** responses carry `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a Content-Security-Policy (`script-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, …), set in `Response.OnStarting` by the first middleware so error responses get them too. Tested on the SPA fallback, a static file, 204, 401, 404 ProblemDetails, 413, 429 and 500 (`AnonymousResponse_HasSecurityHeaders`, `ProblemDetailsResponse_HasSecurityHeaders`, `PostStudent_BodyOver1MiB_Returns413WithoutSavingAnything`, `Login_FourthAttemptInWindow_Returns429`, `UnhandledException_OutsideDevelopment_Returns500WithoutDetails`). To allow `script-src 'self'`, the theme script moved from `index.html` to `theme-init.js` and the production build no longer inlines critical CSS (that step injects an inline script, which the CSP would block and leave the app unstyled). In Development only, `/scalar` and `/openapi` get no CSP, because Scalar's page uses an inline script (`Scalar_InDevelopment_HasNoCspBlockingItsInlineScript`); they are not mapped outside Development. The Docker demo sets `AllowedHosts` to `localhost;127.0.0.1`, so a page that rebinds its own domain to 127.0.0.1 cannot call the API (`AllowedHostsLocalhost_RequestForAnotherHost_Returns400`; checked on the demo: `Host: attacker.example` → 400). No CORS policy (same origin). The `app` container runs as a non-root user (`Dockerfile`). **Accepted:** the Docker demo is plain HTTP on `localhost` (Chrome, Edge and Firefox accept the `Secure` cookie there; Safari does not); a real deployment puts TLS in front. `style-src` keeps `'unsafe-inline'` because Angular and Material inject component styles. |
| **Frontend** | OK | No `innerHTML`, `[href]`/`[src]` bindings, `DomSanitizer` or `bypassSecurityTrust*` (grep); `localStorage` holds only the theme choice, no credentials (`theme.ts`, `theme-init.js`); `returnUrl` only reaches `router.navigateByUrl` and is accepted only as an app path (`safe-return-url.spec.ts`: `//evil.example`, `https://evil.example`, `javascript:…`, `null`, `undefined` → `/lesson-plans`); session loss reloads the page so no previous teacher's data stays in memory (`unauthorized-interceptor.spec.ts`). |
| **Secrets and demo data** | OK + accepted risk | No secrets in the repository or the image (`.dockerignore` excludes `.env`; the image copies only `frontend/` and `src/`; the password reaches the container only as an environment variable at run time). Seed only when `Seed:DemoData` is `true` (off in `appsettings.json`; on in Development and the Docker demo) and only on a database with no users (`Seed_SecondRun_ReturnsFalseAndAddsNothing`, `Seed_DatabaseWithAnyUser_AddsNothing`). The demo password appears in the README, the seed, the planning docs and tests — none of which ship except the seed. **Accepted:** data protection keys are stored unencrypted in the `dp-keys` volume (no key vault or certificate in a local demo; the host logs "No XML encryptor configured"). |
| **Dependencies** | OK | 2026-11-11, approved by the human: `dotnet list package --vulnerable --include-transitive` → no vulnerable packages in any of the 10 projects; `npm audit --omit=dev` → 0; `npm audit` → 0. Base images (`mssql/server:2022-latest`, `node:26-alpine`, `dotnet/sdk:10.0`, `dotnet/aspnet:10.0`) use floating tags and were not scanned. |

## Accepted risks

| Risk | Why accepted | Mitigation in a real deployment |
|---|---|---|
| Demo over plain HTTP on `localhost` | Local demo; browsers treat `localhost` as secure for cookies (except Safari) | TLS in front of the app |
| App connects to SQL Server as `sa` | One-command local demo; migrations need DDL rights | A dedicated login with only the rights migrations and the app need |
| Data protection keys unencrypted in the volume | No secret store in a local demo | Protect keys with a certificate or a key vault |
| Register reveals whether an email has an account (409) | The API contract asks for the 409; the rate limiter slows bulk checks | Same answer for new and existing emails, confirmation by email |
| Logout does not revoke a copied session cookie | HttpOnly and `SameSite=Strict` make copying it unlikely; the cookie expires after 8 h without use | Update the security stamp on logout and validate it on each request |
| Account lockout by a third party | Lockout protects against password guessing; the rate limiter limits abuse | CAPTCHA or progressive delays instead of a hard lockout |
| `style-src 'unsafe-inline'` in the CSP | Angular and Angular Material inject component styles; scripts stay limited to the app's own files | Style nonces (`ngCspNonce`) |
| Last write wins on concurrent edits | One teacher edits their own records | Concurrency token (row version) on updates |
| Rate limit per client IP and per instance | Single-instance local demo; behind Docker Desktop all clients share one IP | Distributed limiter keyed by account and IP |
| Base images on floating tags, not scanned | Local demo built from official images | Pin digests and scan images in CI |
